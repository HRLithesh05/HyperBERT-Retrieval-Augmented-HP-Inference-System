PART 1: WHAT IS THE PROJECT?
Complete System Architecture & Explanation
1.1  The Problem This Project Solves
BERT is one of the most widely used AI language models in the world. When researchers use BERT for a specific task (called fine-tuning), they must set many 'hyperparameters' — settings like learning rate, batch size, optimizer type, number of training epochs, and warmup steps. Getting these settings right is critical: the wrong learning rate can cause the entire training to fail.
The BIG problem: Most research papers that describe BERT experiments do NOT report all their hyperparameters. They might say 'we used standard settings' or leave values blank. This means:
Other researchers cannot reproduce the experiment
Students and labs waste GPU time and money guessing the right values
The scientific community cannot verify if results are trustworthy
This project solves that problem by building an intelligent system that reads a research paper's PDF, figures out what hyperparameters are missing, searches through 300 similar BERT papers to find evidence, and then intelligently infers (calculates) the missing values with confidence scores.
1.2  System Overview — The Big Picture
The full system is called the 'Retrieval-Augmented Hyperparameter Inference System'. It has 8 modules (numbered 0 through 7) arranged in a pipeline. Think of it like a smart assembly line for scientific knowledge.
THE PIPELINE AT A GLANCE
User uploads a BERT paper PDF
↓  Module 1: Extract hyperparameters from the PDF
↓  Module 2: Check which hyperparameters are missing
↓  Module 3 (CORE): Retrieve similar papers + infer missing values
↓  Module 4: Apply BERT-specific constraints
↓  Module 5: Detect contradictions in evidence
↓  Module 6: Validate inferred values
↓  Module 7: Generate ready-to-run Jupyter Notebook
1.3  MODULE 0 — Corpus Builder (Offline Phase)
This module runs ONCE before the system goes live. It builds the knowledge base that the system will later search.
What it does step by step:
Step 1 — Query APIs: The system queries Semantic Scholar (an academic search engine) to find 1000+ BERT-related paper IDs
Step 2 — Download PDFs: The top 400 papers are downloaded as PDFs; PyMuPDF extracts text from the body; pdfplumber extracts tables
Step 3 — Two-Pass LLM: An LLM reads each paper twice — first pass extracts hyperparameter JSON, second pass verifies it — producing 300 clean records
Step 4 — Build FAISS Index: sentence-transformer embeddings are created for each paper and stored in a FAISS IndexFlatIP structure
Step 5 — Compute R-Scores: A weighted formula calculates a 'relevance score' for all 300 papers; scores are stored in MongoDB
Key Technical Terms:
PyMuPDF
Python MuPDF library (also called fitz)
A Python library that reads PDF files and extracts text, images, and tables. 'fitz' is the module name you import in Python. Used here to read research paper PDFs.
pdfplumber
PDF Table Extractor
A Python library specialized in extracting structured tables from PDFs. When a paper has a table of hyperparameters, pdfplumber can read it properly.
FAISS
Facebook AI Similarity Search
An open-source library by Meta (Facebook) AI Research that lets you store millions of vector embeddings and search for the most similar ones extremely fast. IndexFlatIP = Flat Index, Inner Product similarity. 'Flat' means it searches all vectors exactly (no approximation). 'IP' = Inner Product, which is equivalent to cosine similarity when vectors are normalized.
MongoDB
Document-oriented NoSQL Database
A database that stores data as JSON-like documents instead of traditional rows/columns. Used here to store the 300 paper records and their R-Scores.
HyperBERT-Corpus
Hyperparameter BERT Corpus
The project's custom name for the collection of 300 cleaned, structured BERT paper records stored in MongoDB.
R-Score
Relevance Score
A numerical score assigned to each paper in the corpus indicating its general relevance. Calculated using a weighted formula combining citation count, recency, and quality indicators.
1.4  MODULE 1 — PDF Input Analyzer
The user uploads their BERT paper PDF. This module reads and understands it.
Two sub-processes run in parallel:
PDF Text Extraction: PyMuPDF extracts the body text; pdfplumber finds any hyperparameter tables in the paper
LLM HP (Hyperparameter) Extraction: The extracted text is sent to an LLM with a structured prompt. The LLM runs two passes: (1) extract all hyperparameter values → output JSON, (2) verify the JSON is correct and complete
Output: A structured JSON file containing all found hyperparameters AND a 'missing_params list' — the hyperparameters the LLM could not find.
Also performs: JSON Schema Construction
This maps the paper's reported values to a standardized schema covering: learning rate (LR), batch size, number of epochs, optimizer type (AdamW/Adam/SGD), warmup steps/ratio, sequence length (SeqLen), weight decay (WD).
Key Technical Terms:
HP (Hyperparameter)
Hyperparameter
A configuration setting that controls the learning process of a machine learning model. Unlike model parameters (which are learned during training), hyperparameters are set BEFORE training begins. Examples: learning rate = 2e-5, batch size = 32, epochs = 3.
Two-Pass LLM
Two-Pass Large Language Model Processing
Running an LLM on the same content twice with different instructions. Pass 1: extract information. Pass 2: verify and correct the extraction. This reduces errors compared to a single pass.
JSON Schema
JavaScript Object Notation Schema
JSON (JavaScript Object Notation) is a text format for storing structured data using key-value pairs. A 'schema' defines what fields must exist and their data types. Example: {"learning_rate": 2e-5, "batch_size": 32, "optimizer": "AdamW"}
1.5  MODULE 2 — Completeness Checker & R-Score
This module acts as a gatekeeper. It receives the structured JSON from Module 1 and answers: 'Is this paper complete?'
Two processes:
Completeness Check: Checks each hyperparameter field. If a value is null, vague, or missing, it flags it.
R-Score Computation: Computes the paper's overall completeness/relevance score.
Decision point:
If Missing HPs = YES → Forward to Module 3 (Retrieval + Inference)
If Missing HPs = NO → Skip directly to Module 7 (Notebook Generation)
1.6  MODULE 3 — Agentic Retrieval Engine (THE CORE MODULE)
This is the brain of the system. It uses a ReAct-style loop (Thought → Action → Observation) to adaptively retrieve evidence and infer missing values.
The 5-Step Pipeline Inside Module 3:
Step 1 — Task-Aware Filter: Before doing vector search, it pre-filters the 300-paper corpus using SQLite based on the task type (e.g., NER, classification) and model variant (BERT-base, BERT-large). This reduces noise.
Step 2 — FAISS Vector Retrieval: The user's paper is converted to an embedding (a numerical vector). FAISS finds the top-k most similar papers using cosine similarity. These are the 'candidate' papers.
Step 3 — Metadata Aggregation: Hyperparameter values from all retrieved papers are pooled together into one 'evidence pool' per missing parameter.
Step 4 — Constraint-Aware Inference: For each missing parameter, the system infers its value: Categorical parameters (optimizer type, activation) → Weighted Mode (most common value). Continuous parameters (learning rate, batch size) → Weighted Median + IQR (middle 50% range).
Step 5 — Confidence Calibration: A confidence score is computed as a function of: similarity of retrieved papers, variance in the evidence values, support_count (how many papers agree). If confidence < threshold θ → re-retrieve with relaxed strategy.
Adaptive Strategy Loop (S1 → S4):
If confidence is too low after initial retrieval, the system automatically widens its search:
S1 Narrow Match: Task + Model + Dataset (most specific)
S2 Relaxed Match: Task + Model only
S3 Task Only: Any BERT paper with the same task
S4 Global Fallback: All 300 BERT papers in the corpus
Live ArXiv / Semantic Scholar Fetch:
If even the Global Fallback has fewer than N papers, the system goes LIVE — it queries ArXiv and Semantic Scholar APIs in real time (async, 60-second timeout) to fetch fresh papers and adds them to the evidence pool for this session.
Key Technical Terms:
ReAct-Style
Reasoning + Acting Style (from ReAct paper, ICLR 2023)
An agentic AI pattern where the system alternates between: Thought (internal reasoning about what to do), Action (doing something, e.g., retrieve papers), and Observation (seeing the result). This loop continues until the system has enough confidence. The name 'ReAct' = Reasoning + Acting.
Cosine Similarity
Vector Cosine Similarity
A mathematical measure of how similar two vectors are, ranging from -1 to +1. A score of 1 means identical direction (highly similar). Used here to find papers that are semantically similar to the user's paper.
Embedding / Vector
Numerical Representation of Text
A list of numbers (e.g., 384 numbers) that represents the meaning of a sentence or document. Similar sentences have similar vectors. Generated using sentence-transformers model all-MiniLM-L6-v2.
Weighted Median + IQR
Statistical Central Tendency with Interquartile Range
Weighted Median: the middle value when data points are sorted and weighted by relevance. IQR (Interquartile Range) = Q3 - Q1 = the range containing the middle 50% of values. Used together to find the 'typical' value for a continuous hyperparameter while being robust to outliers.
Weighted Mode
Most Frequently Occurring Value (Weighted)
The value that appears most often in the evidence pool, but with each occurrence weighted by how similar that paper was to the query paper. Used for categorical choices like optimizer type.
Top-k
Top K Results
When searching, returning only the k highest-scoring results. E.g., top-5 retrieval = return the 5 most similar papers.
SQLite
Lightweight SQL Database
A serverless, file-based relational database. Used here as a fast pre-filter before the FAISS vector search, filtering papers by task type and model name.
Async
Asynchronous (Programming)
Running a task in the background without blocking the main process. The Live Fetch runs asynchronously so the system can continue processing while waiting for API responses.
1.7  MODULE 4 — Constraint-Aware Inference
After Module 3 infers candidate values, Module 4 applies BERT-specific domain knowledge to ensure the inferred values are physically realistic and consistent with each other.
Four constraint rules:
AdamW → WD > 0: If the optimizer is AdamW, weight decay MUST be greater than 0 (AdamW's purpose is to apply weight decay separately from gradient updates).
Adam → WD = 0: If the optimizer is plain Adam, weight decay should be 0 (Adam already has its own weight decay inside momentum terms).
Linear LR Scaling Rule: LR2 = LR × (B2/B1). If batch size changes, the learning rate should scale linearly. This ensures the 'effective learning' per gradient update stays consistent.
Warmup Consistency: warmup steps = 6–10% of total training steps. This is the standard BERT fine-tuning warmup range.
SeqLen vs Task: Sequence length ≤ 128 for classification tasks; 384–512 for QA tasks. This is because QA needs longer context windows.
Key Technical Terms:
AdamW
Adam with Weight Decay Decoupled
An optimizer (training algorithm) that extends Adam by correctly applying weight decay. 'W' = Weight decay. Invented to fix a bug in how Adam applied L2 regularization. The standard optimizer for BERT fine-tuning.
Weight Decay (WD)
L2 Regularization Parameter
A technique that adds a penalty for large weights in the model. Prevents overfitting by encouraging smaller, more generalizable weights. In BERT fine-tuning, typical values are 0.01–0.1.
Warmup Steps
Learning Rate Warmup Steps
At the start of training, the learning rate is linearly increased from 0 to the target LR over 'warmup steps'. This prevents destabilizing the pretrained BERT weights with a large gradient update on step 1.
LR Scaling Rule
Linear Learning Rate Scaling Rule
A rule stating that when you change batch size, you should scale the learning rate proportionally. E.g., doubling batch size → double the learning rate. Maintains gradient signal consistency.
1.8  MODULE 5 — Evidence Contradiction Detector
This module checks whether the evidence pool contains conflicting values. Not all retrieved papers will agree — some may use LR=1e-5 while others use LR=5e-5.
Two processes:
Outlier Detection: Uses IQR-based detection to flag anomalous hyperparameter values in the evidence pool (values outside Q1 - 1.5×IQR or Q3 + 1.5×IQR are outliers).
Conflict Surfacing: When two papers significantly disagree, the system generates an explanation with source attribution — 'Paper A used LR=1e-5 because it trained on a small dataset; Paper B used LR=5e-5 because it used a larger batch size.'
Confidence Adjustment: High variance or many outliers → lower confidence in the inferred value is reported to the user.
Key Technical Terms:
IQR (Interquartile Range)
Q3 - Q1
The range of the middle 50% of a dataset. Used in outlier detection: any value more than 1.5×IQR below Q1 or above Q3 is considered an outlier (Tukey's fence method).
Source Attribution
Citing the Source of Information
For every inferred hyperparameter value, the system records WHICH papers it came from. This makes the output traceable and verifiable — a key feature for scientific reproducibility.
1.9  MODULE 6 — Self-Critique Validator
Inspired by Self-RAG (the core paper), this module applies 5 hard BERT domain rules to the inferred configuration. If any rule is violated, the configuration is flagged as ERROR and Module 3 re-retrieves.
5 constraint rules:
LR range: Learning rate must be in [1e-6, 1e-4] for BERT fine-tuning
Batch size: Must be a power of 2 (8, 16, 32, 64) for GPU memory efficiency
Epochs: Must be 2–5 for fine-tuning (too many = overfitting, too few = underfitting)
Warmup: Must be 6–10% of total steps
Optimizer consistency: AdamW↔WD coupling (from Module 4)
Outputs:
PASS: Configuration is valid → proceed to Module 7
ERROR: Violation found → re-trigger Module 3 retrieval
WARN: Borderline value → flag in report but proceed
Auto-Correction:
For minor violations, the system automatically applies corrections (e.g., round batch size to nearest power of 2) and flags them in the final report.
1.10  MODULE 7 — Annotated Notebook Generator
This is the output module. It generates a ready-to-run Jupyter Notebook (.ipynb file) with the complete, validated hyperparameter configuration plus training code.
5-phase notebook structure:
Ph1 Dataset Prep: Data loading and preprocessing code
Ph2 Model Init: BERT model initialization with the inferred configuration
Ph3 Training Config: Optimizer, scheduler, and hyperparameter setup
Ph4 Training Loop: The actual training loop with logging
Ph5 Eval: Evaluation metrics and results logging
Every inferred value in the notebook includes: the source papers (citations), the confidence score, and a reasoning note (e.g., 'Inferred from 7 similar NER papers; median value; high confidence 0.87').
Key Technical Terms:
Jinja2
Python Templating Engine
A library that fills in template files with dynamic data. Like Python's f-strings but for entire files. Used here to generate the Jupyter Notebook code from a template, substituting the inferred hyperparameter values.
.ipynb
IPython Notebook format
The file format for Jupyter Notebooks. A JSON file containing code cells, markdown cells, and output. Stands for IPython Notebook.
Confidence Score
Numerical confidence in an inferred value (0–1)
A number between 0 and 1 representing how confident the system is in an inferred hyperparameter value. 0.9+ = high confidence. 0.5–0.7 = moderate. Below 0.5 = low (triggers re-retrieval).

PAPER 8 — Dense Text Retrieval Based on Pretrained Language Models: A Survey
PAPER DETAILS
Authors: Wayne Xin Zhao, Jing Liu, Ruiyang Ren, Ji-Rong Wen
Published: ACM Transactions on Information Systems, Vol. 42, No. 4, February 2024
DOI: https://doi.org/10.1145/3637870
Role in Project: This paper provides the theoretical foundation for WHY the project uses FAISS dense retrieval instead of traditional keyword search
8.1  Why This Paper Was Chosen
This project's core retrieval engine (Module 3) uses dense vector search via FAISS to find similar BERT papers. Paper 8 is the definitive survey explaining what dense retrieval is, how it works, and why it outperforms keyword-based search. Understanding this paper is understanding WHY FAISS was chosen for the project.
8.2  The Core Problem This Paper Addresses
Traditional search systems like BM25 (Best Match 25) or TF-IDF match documents to queries by looking for exact word matches. This fails for scientific queries because:
A paper about 'AdamW optimizer' will not be found when searching for 'weight decay optimization' even though they mean the same thing
Semantic meaning is lost when only keywords are matched
'Bag-of-words' models cannot understand context
Dense retrieval solves this by converting both queries and documents into dense vectors (embeddings) that capture semantic meaning, not just keywords.
8.3  The Two Main Architectures (Slide Image 2 — Dual vs Cross Encoder)
The slide for Paper 8 shows Image 2: the dual-encoder vs cross-encoder architecture diagram. This is a critical diagram to understand.
(a) Dual-Encoder Architecture (Bi-Encoder)
In Image 2(a), you can see two SEPARATE neural networks side by side:
Left network: Encodes the Query q → produces vector Eq(q) = φ(q)
Right network: Encodes the Document d → produces vector Ed(d) = ψ(d)
Relevance score: Rel(q,d) = fsim(φ(q), ψ(d)) — e.g., cosine similarity between the two vectors
Key insight: The query and document are encoded INDEPENDENTLY. This means you can pre-compute all document vectors ONCE, store them in FAISS, and at query time only compute the query vector, then do a fast vector search. This is WHY it's fast enough for real-time use.
(b) Cross-Encoder Architecture
In Image 2(b), BOTH the query and document are fed into ONE single neural network together:
Input: [CLS] q(1) ... q(k) [SEP] d(1) ... d(l)
The model computes deep interaction between every query token and every document token
Output: A single similarity score sim(q,d)
More accurate than bi-encoder BUT cannot pre-compute documents. Every query-document pair must be processed from scratch. This is too slow for searching 300 papers in real-time.
[CLS] and [SEP] — What Do These Mean?
[CLS]
Classification Token
A special token added at the BEGINNING of every BERT input. Its final representation captures the overall meaning of the entire input sequence. Used as the sentence-level embedding. Stands for 'classification.'
[SEP]
Separator Token
A special token that separates two text segments in BERT input. E.g., [CLS] question [SEP] passage [SEP]. Tells the model 'here is where one sequence ends and another begins.'
Why This Project Uses Bi-Encoder:
The project uses a bi-encoder (Sentence-Transformers) to pre-compute embeddings for all 300 corpus papers (during Module 0, offline). Then at query time, only the user's paper needs to be encoded. FAISS does the fast nearest-neighbor search. A cross-encoder would require re-processing all 300 papers for every new query — too slow.
8.4  Four Key Aspects Surveyed in the Paper
Aspect 1: Architecture
How to design the neural network for retrieval. The survey covers:
Single-representation bi-encoder: One vector per document (the [CLS] embedding)
Multi-representation bi-encoder: Multiple vectors per document (ColBERT)
Cross-encoder: Pairs of query + document fed together
Aspect 2: Training
How to train the retrieval model. Key challenges:
Negative selection: You need NEGATIVE examples (irrelevant papers) to train the model to distinguish relevant from irrelevant. In-batch negatives, hard negatives, denoised negatives.
Knowledge distillation: Training a small fast model (bi-encoder) to mimic a large accurate model (cross-encoder). This is the KEY technique — cross-encoder is teacher, bi-encoder is student.
Pretraining: Adapting BERT's pre-training for retrieval tasks (ICT, BFS tasks)
Aspect 3: Indexing
How to store and search vectors efficiently:
FAISS IndexFlatIP: Exact search using inner product (used in this project)
IVF (Inverted File Index): Clusters vectors for faster approximate search
Product Quantization (PQ): Compresses vectors to reduce memory
Aspect 4: Integration
How to combine retrieval with the full pipeline (retriever + reranker):
Bi-encoder retriever: Fast, finds top-k candidates
Cross-encoder reranker: Slow but accurate, re-ranks the top-k
This project uses only the retriever stage (no reranker needed since Module 6 validates)
8.5  Key Datasets Used in the Survey
MS MARCO
Microsoft Machine Reading Comprehension
A large-scale dataset with 8.8M web passages and 500K+ queries with annotations. The standard benchmark for dense retrieval research. Created by Microsoft.
NQ (Natural Questions)
Google Natural Questions
A dataset of real Google search queries with Wikipedia passages as answers. Contains 152K training queries.
BEIR
Benchmarking IR
A heterogeneous benchmark for zero-shot evaluation of retrieval models across 18 diverse datasets and 9 task types. Tests how well a retrieval model works on domains it was NOT trained on.
KILT
Knowledge Intensive Language Tasks
A benchmark for tasks requiring knowledge retrieval + generation. Includes Fever (fact verification), TREC-COVID, etc.
8.6  Key Evaluation Metrics
MRR@10
Mean Reciprocal Rank at 10
Measures how high the first correct answer appears in the top-10 results. If correct answer is rank 1 → score 1.0. Rank 2 → 0.5. Rank 3 → 0.33. MRR = average over all queries.
NDCG@k
Normalized Discounted Cumulative Gain at k
Measures ranking quality considering relevance levels. Higher-ranked relevant results contribute more. Normalized against ideal ranking. Common cutoffs: NDCG@10, NDCG@100.
Recall@k
Recall at k results
What fraction of ALL relevant documents appear in the top-k results? Important for retrieval where you want to ensure no relevant papers are missed.
Top-K Accuracy
Accuracy at K
The fraction of queries where the correct answer appears somewhere in the top-k retrieved results.
8.7  Key Models Mentioned
DPR
Dense Passage Retrieval
The first major bi-encoder model for open-domain QA, by Facebook AI. Uses two BERT encoders (question encoder + passage encoder). Trained with in-batch negatives and hard negatives from BM25.
ColBERT
Contextualized Late Interaction over BERT
A multi-representation retrieval model that stores per-token embeddings and uses 'late interaction' — computing token-level similarities at query time. Better than single-vector bi-encoder but requires more storage.
BM25
Best Match 25
A classical keyword-based retrieval model (no neural network). Uses term frequency and inverse document frequency with saturation functions. Still a strong baseline for exact-keyword queries. BERT-based models often beat BM25 on semantic queries but sometimes lose on exact entity matching.
SPLADE
Sparse Lexical and Expansion
A hybrid model that learns sparse vocabulary-sized representations using PLMs. Combines the interpretability of sparse retrieval with the semantic understanding of PLMs.
RocketQA
Rocket Question Answering
A system by Baidu that uses cross-batch negatives + denoised hard negatives + data augmentation. Achieves state-of-the-art on MS MARCO passage retrieval.

PAPER 9 — Structured Information Extraction from Scientific Text with Large Language Models
PAPER DETAILS
Authors: John Dagdelen, Alexander Dunn, Sanghoon Lee, Nicholas Walker, Andrew S. Rosen, Gerbrand Ceder, Kristin A. Persson, Anubhav Jain
Published: Nature Communications, Vol. 15, Article 1418, February 15, 2024
DOI: https://doi.org/10.1038/s41467-024-45563-x
Role in Project: This paper justifies WHY the project uses LLMs (not rule-based or BERT-based NER) to extract hyperparameters from research papers (Module 1)
9.1  Why This Paper Was Chosen
Module 1 of the project uses an LLM with a two-pass approach to extract hyperparameters from PDFs and output structured JSON. Paper 9 provides the exact methodology that justifies this approach — it shows that LLMs fine-tuned on just 400-650 examples can extract complex structured relationships from scientific text, far outperforming older BERT-based NER models.
9.2  The Core Problem
Scientific knowledge (like materials properties, synthesis conditions, and — in our case — hyperparameters) is buried in unstructured text. Extracting it manually is:
Time-consuming (reading thousands of papers)
Error-prone (humans miss things)
Not scalable (cannot process 1000s of papers automatically)
Previous solutions (rule-based, BiLSTM, BERT-NER) were good at finding entities (like 'LiCoO2' or '2e-5') but bad at understanding the RELATIONSHIPS between entities. They could not tell you 'this learning rate was used WITH this optimizer FOR this task.'
9.3  The Three-Step Method (Slide Image 3)
The slide for Paper 9 shows Image 3 — the three-phase approach to LLM-based information extraction:
Phase 1: Training (with ~100 examples)
The expert manually annotates about 100 examples. Each example is a (text passage → structured JSON) pair. The LLM is trained on these examples using cross-entropy loss. This produces a 'Partially-Tuned LLM.'
Phase 2: Assisted Annotation (Human-in-the-Loop, ~500 examples)
The partially-trained model is used to AUTO-SUGGEST annotations for new text passages. A human expert then reviews and corrects the suggestions. This is MUCH faster than annotating from scratch. The corrected examples are added to the training set. The LLM is re-trained.
Phase 3: Inference — Fine-Tuned LLM Output
The fully fine-tuned model is deployed. Given a new text passage, it outputs a structured JSON with all extracted entities and their relationships. In Image 3, you can see the model correctly extracting {formula: 'CoCrFeMnNi', structure: ['face-centered cubic', 'FCC'], application: ['high entropy alloy']} from the text passage.
9.4  What is NER and NERRE?
NER
Named Entity Recognition
The task of identifying and classifying named entities in text into predefined categories. Example: 'LiCoO2 is a Li-ion battery material' → entity: 'LiCoO2', type: FORMULA; entity: 'Li-ion battery', type: APPLICATION.
NERRE
Named Entity Recognition and Relation Extraction (Joint)
A harder task that simultaneously identifies entities AND the relationships between them. The output is a structured JSON grouping related entities together. Example: {'formula': 'LiCoO2', 'application': ['Li-ion battery', 'cathode']} — not just the entities, but knowing they belong TOGETHER.
Relation Extraction (RE)
Identifying Relationships Between Entities
Determining which entities are linked by what relationship. e.g., 'LiCoO2 is a cathode in a Li-ion battery' → (LiCoO2, has_application, Li-ion battery). RE is harder than NER because it requires understanding meaning.
9.5  The Three Tasks in the Paper
Task 1: Solid-State Impurity Doping
Domain: Materials science. Goal: Extract which materials are doped with which dopants from a sentence. Example: 'ZnO nanoparticles doped with Co' → {host: 'ZnO nanoparticles', dopant: 'Co'}. 413 annotated sentences.
Task 2: Metal-Organic Frameworks (MOF) Cataloging
Domain: Chemistry. Goal: From an abstract, extract MOF names, chemical formulae, guest species, applications, and descriptions. 507 annotated abstracts.
Task 3: General Materials Information Extraction
Domain: General materials science. Goal: Extract composition, phase, morphology, and application information. 634 annotated abstracts.
9.6  Two LLMs Compared: GPT-3 vs Llama-2
GPT-3
Generative Pre-trained Transformer 3 (OpenAI)
A 175-billion-parameter language model by OpenAI. Closed-source — accessed via API. One of the most capable text generation models. In this paper, fine-tuned via OpenAI's fine-tuning API.
Llama-2
Large Language Model Meta AI version 2
A family of open-source LLMs by Meta AI. The 70B (70 billion parameter) version was used here. Fine-tuned using LoRA (Parameter-Efficient Fine-Tuning) on a single A100 GPU.
Fine-tuning
Task-specific LLM training
Taking a pretrained LLM and training it further on a small, specific dataset (413-634 examples) to make it an expert at one task. Far more efficient than training from scratch.
LoRA
Low-Rank Adaptation
A parameter-efficient fine-tuning technique that only trains a small number of additional parameters instead of all 70B weights. The original weights are frozen; only small 'adapter' matrices are trained. Drastically reduces GPU memory and time needed.
Hallucination (LLM)
LLM Generating False Information
When an LLM generates text that sounds plausible but is factually incorrect or not present in the source. Example: adding 'SiO2' formula when the paper only mentions 'silica'. Paper 9 discusses this as a limitation and how entity normalization can be confused with hallucination.
9.7  Output Schemas: JSON vs English Sentences
A key insight of Paper 9 is that the OUTPUT FORMAT (schema) matters. Two formats were tested:
JSON Schema: {"hosts": {...}, "dopants": {...}, "hosts2dopants": {...}} — machine-readable, structured, easy to parse
English Schema: 'The host <host> was doped with <dopant>.' — more natural language, easier for the LLM to generate correctly
Finding: GPT-3 performs better with English schemas; Llama-2 performs better with JSON schemas. Our project uses JSON output from the LLM, consistent with the approach validated in this paper.
9.8  Evaluation Metrics
Exact Match (EM) Precision/Recall/F1
Word-level exact matching score
Precision = (correct words extracted) / (total words extracted). Recall = (correct words extracted) / (total words in ground truth). F1 = harmonic mean of P and R. 'Exact' means words must match perfectly — 'Li-ion' and 'lithium ion' would NOT match.
Manual Score
Human expert evaluation score
A domain expert manually checks if extracted information is semantically equivalent to the ground truth, allowing for normalization (e.g., 'LiCoO2' = 'lithium cobalt oxide'). Manual scores are significantly HIGHER than exact match scores because they capture true capability.
BERTScore
Semantic Similarity Metric using BERT
Instead of exact word matching, computes similarity between generated and reference text using BERT embeddings. A BERTScore of 0.9 means the generated text is semantically very similar to the reference.

PAPER 10 (CORE PAPER) — Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection
PAPER DETAILS — CORE PAPER
Authors: Akari Asai, Zeqiu Wu, Yizhong Wang, Avirup Sil, Hannaneh Hajishirzi
Published: ICLR (International Conference on Learning Representations), May 2024
arXiv: https://arxiv.org/abs/2310.11511
Role in Project: THE CORE paper — Module 6 (Self-Critique Validator) is directly inspired by Self-RAG's self-reflection mechanism
10.1  Why This is the Core Paper
Self-RAG is the most directly influential paper to this project's architecture. The project's Module 6 (Self-Critique Validator) implements a domain-specific version of Self-RAG's key innovation: a model that doesn't just generate output, but CRITIQUES its own output and decides whether to retrieve more information. This is what makes the system 'self-correcting' rather than blindly trusting the LLM's first attempt.
10.2  The Core Problem with Standard RAG
Standard RAG (Retrieval-Augmented Generation) has a fixed, rigid structure:
Step 1: ALWAYS retrieve k documents
Step 2: ALWAYS generate an answer using those documents
Problems with this approach:
Over-retrieval: For simple questions, retrieving k documents is wasteful and noisy
Under-retrieval: For complex questions, k documents may not be enough
No quality control: The model generates an answer regardless of whether the retrieved documents are actually relevant
Hallucination: The model may generate facts not present in the retrieved documents
No self-evaluation: The model has no way to know when it should 'try again'
10.3  Self-RAG's Innovation — The Slide Image 4
The slide for Paper 10 shows Image 4 — a comparison between standard RAG (left) and Self-RAG (right). Study this image carefully:
Standard RAG (left side of Image 4):
For the query 'How did US states get their names?':
Step 1: Retrieve K documents (three shown: about states named after people, baby names, fictional islands)
Step 2: Prompt LLM with all K docs together
Result: LLM generates a mix of accurate ('11 states named after a person') and WRONG information ('California named after Christopher Columbus' — STRIKETHROUGH in image, indicating error)
Second prompt ('Write an essay about summer vacation'): ALSO retrieves K documents even though no retrieval is needed → wasteful
Self-RAG (right side of Image 4):
Same query 'How did US states get their names?':
Step 1: Retrieve on demand — Model first generates 'US states got their names from a variety of sources.' Then a RETRIEVE token is generated, triggering retrieval
Step 2: Generate segment in parallel — For each of the 3 retrieved documents (1, 2, 3), the model generates a response segment in parallel
Each segment is evaluated with critique tokens: [Relevant] or [Irrelevant] — Is this document relevant? [Supported] or [Partially supported] or [No information] — Does the document support this claim?
Segment 1 (doc 1): [Relevant] + [Supported] → '11 of 50 state names come from persons' → chosen as best
Segment 2 (doc 2): [Irrelevant] (about baby names in Texas) → discarded
Segment 3 (doc 3): [Relevant] + [Partially supported] → 'California named after 16th-century novel' → accepted with partial
Step 3: Critique outputs and select best segment — Segment 1 wins (best critique scores)
Summer vacation prompt: Model generates [No Retrieval] token — no unnecessary retrieval
10.4  The Three Types of Critique Tokens
ISREL (Is Relevant?)
Retrieval Relevance Token
A binary token generated by Self-RAG to assess whether a retrieved document is actually relevant to the query. Values: [Relevant] or [Irrelevant]. Documents marked irrelevant are discarded.
ISSUP (Is Supported?)
Support Token
A token assessing whether the generated text is factually supported by the retrieved document. Values: [Fully Supported], [Partially Supported], [No Support / Contradicts]. Catches hallucinations.
ISUSE (Is Useful?)
Usefulness Token
A token rating how useful the generated response is for answering the query. Scale: [5] (very useful) to [1] (not useful). Used to rank candidate responses.
[Retrieve] Token
Adaptive Retrieval Trigger
A special token generated by Self-RAG when the model decides it NEEDS external information. NOT generated when the query can be answered from internal knowledge (like 'write an essay about summer vacation').
10.5  Self-RAG's Training Approach
Self-RAG trains two models:
Critic Model: Trains on examples where human experts labeled outputs with [Relevant/Irrelevant], [Supported/Not Supported], etc. Learns to generate critique tokens.
Generator Model: Trained on (input + retrieved docs + critique tokens) → output. Learns to generate HIGH-quality outputs that receive good critique scores.
The critic model can be a separate smaller LLM or the same LLM with special training. The key is that critique tokens become part of the model's vocabulary and are generated as naturally as regular text.
10.6  Key Technical Terms
RAG
Retrieval-Augmented Generation
An AI paradigm where a language model is supplemented with a retrieval system. Instead of relying only on parametric memory (what it learned during pretraining), the model can RETRIEVE relevant documents at query time and use them to generate better answers. Reduces hallucination.
Self-Reflection
Model Evaluating Its Own Output
The ability of a model to assess the quality of its own generated output. Self-RAG implements this via critique tokens. Analogous to a student checking their own work before submitting.
Hallucination (in RAG)
Generating Unsupported Facts
When a RAG model generates a claim that sounds plausible but is NOT present in the retrieved documents. Self-RAG's [Supported] token is specifically designed to detect and penalize hallucinations.
FactScore
Factuality Score
A metric that evaluates factual precision by checking what percentage of generated atomic facts can be verified in a knowledge source (like Wikipedia). Self-RAG improves FactScore over baselines.
MAUVE
Matching Augmented Underwriting and Verbosity Evaluation
A text quality metric that measures how close generated text is to human-written text using distributional divergence. Used to evaluate text generation quality in Self-RAG benchmarks.
ROUGE
Recall-Oriented Understudy for Gisting Evaluation
A family of metrics (ROUGE-1, ROUGE-2, ROUGE-L) that measure overlap between generated and reference text. ROUGE-1 = unigram overlap, ROUGE-L = longest common subsequence.
ICLR
International Conference on Learning Representations
One of the top-tier machine learning research conferences. Publishing at ICLR is considered a major achievement. Self-RAG was accepted here in 2024.

PART 3: MASTER GLOSSARY — Every Term a Teacher Might Ask
This section lists every technical term used in the project and papers with a clear, brief definition. If a teacher points to ANY word, you can flip here.
A — F
Adam / AdamW
Adaptive Moment Estimation / Adam with Weight Decay
Optimizers for training neural networks. Adam adapts learning rates for each parameter. AdamW fixes the weight decay implementation in Adam. Used extensively in BERT fine-tuning.
Agentic
Agent-like Behavior
An AI system that takes autonomous actions (retrieve, compute, validate) in a loop, adapting its behavior based on what it observes. Module 3 is 'agentic' because it decides dynamically whether to retrieve more papers.
API
Application Programming Interface
A set of rules for how software can communicate. Semantic Scholar API lets you query their paper database programmatically. ArXiv API lets you retrieve papers programmatically.
BERT
Bidirectional Encoder Representations from Transformers
A 2018 Google AI language model that reads text in both directions simultaneously. Pretrained on 3.3B words. Fine-tuning = adapting it for a specific task (NER, classification, QA) using a small labeled dataset.
BERT-base vs BERT-large
BERT model variants
BERT-base: 12 Transformer layers, 768 hidden dimensions, 110M parameters. BERT-large: 24 layers, 1024 hidden dimensions, 340M parameters. BERT-large is more capable but requires more GPU memory.
Batch Size
Training Batch Size
The number of training examples processed together in one forward+backward pass. Common BERT values: 8, 16, 32. Larger batch = smoother gradients but more GPU memory.
Cross-Entropy Loss
Loss Function for Classification
A mathematical function measuring how wrong the model's predictions are. The model is trained to minimize this value. Used in Module 0's two-pass LLM training.
FAISS
Facebook AI Similarity Search
Library for fast nearest-neighbor search in high-dimensional spaces. Used in this project to find the most similar BERT papers to the query paper using vector similarity.
FastAPI
Python Web Framework
A modern Python framework for building REST APIs. Used as the project's backend server. 'REST' = REpresentational State Transfer — a standard way web services communicate.
Fine-tuning
Task-Specific LLM/BERT Training
Continuing the training of a pretrained model on a small task-specific dataset. BERT was pretrained on Wikipedia; fine-tuning adapts it for NER or QA.
G — L
GPU
Graphics Processing Unit
Hardware originally designed for rendering graphics, now used for AI training because of its massive parallel processing capability. Training BERT requires GPUs (typically NVIDIA A100, V100).
HuggingFace Transformers
Python Library for Pretrained Models
The most popular open-source library for loading, fine-tuning, and using pretrained transformer models like BERT, GPT, Llama. This project uses it to load BERT for evaluation.
Hyperparameter
Model Training Configuration Value
A setting that controls how a model is trained, set BEFORE training starts. BERT fine-tuning hyperparameters: learning rate (e.g., 2e-5), batch size (e.g., 32), epochs (e.g., 3), optimizer (AdamW), warmup ratio (0.1), max sequence length (128 or 512).
IndexFlatIP
FAISS Flat Index with Inner Product
A FAISS index type that stores all vectors in flat memory and computes exact inner product (cosine similarity when normalized) between query and all stored vectors. Guarantees exact results at the cost of O(N) search time.
Jinja2
Python Templating Engine
Used to generate the Jupyter Notebook (.ipynb) file in Module 7 by filling in a template with the inferred hyperparameter values.
JSON
JavaScript Object Notation
A lightweight data interchange format. Example: {"learning_rate": 2e-5, "batch_size": 32, "optimizer": "AdamW"}. Used throughout the project to pass structured data between modules.
Jupyter Notebook
Interactive Python Computing Environment
A web-based IDE where code, markdown, and outputs are combined in cells. Scientists use it for experiments. Module 7 generates a ready-to-run .ipynb file.
Learning Rate (LR)
Gradient Descent Step Size
Controls how large each weight update step is during training. Too high → training diverges (loss explodes). Too low → training is too slow. BERT fine-tuning LR: typically 1e-5 to 5e-5.
LLM
Large Language Model
A neural network with billions of parameters trained on massive text corpora. Examples: GPT-4, Llama-2, Claude. Capable of understanding and generating human-like text.
M — R
MiniLM-L6-v2
all-MiniLM-L6-v2 Sentence Transformer
A lightweight but powerful sentence embedding model by HuggingFace. 'L6' = 6 layers. 'v2' = version 2. Outputs 384-dimensional vectors. Fast enough for real-time use. Used in Module 0 to create paper embeddings.
MongoDB
Document-Oriented NoSQL Database
Stores data as flexible JSON documents. Used in this project to store 300 BERT paper records and their metadata.
NLP
Natural Language Processing
The field of AI that deals with understanding and generating human language. BERT is an NLP model. This project is in the NLP domain.
Optimizer
Training Algorithm
The algorithm that updates model weights based on the computed gradient. Common: SGD (basic), Adam (adaptive), AdamW (Adam with proper weight decay). The optimizer is a KEY hyperparameter.
Overfitting
Model Memorizing Training Data
When a model performs well on training data but poorly on new data. Symptom of too many epochs or too high LR. BERT fine-tuning for >5 epochs often overfits.
PLM
Pretrained Language Model
A large language model trained on general text data BEFORE fine-tuning. BERT, GPT, RoBERTa, T5 are all PLMs. The key idea: pretraining on massive data → general knowledge → fine-tuning on task-specific data → expertise.
PyTorch
Python Deep Learning Framework
An open-source machine learning library by Meta. The most popular framework for training neural networks. Used in this project for model operations.
RAG
Retrieval-Augmented Generation
Combining a retrieval system with a language model. The retrieval system finds relevant documents; the LLM generates answers using those documents as context.
React.js
JavaScript Frontend Framework
A library by Meta for building user interfaces. Used in this project's frontend where users upload papers and view results.
ReAct
Reasoning + Acting (AI Agent Pattern)
An AI pattern where the model alternates between Thought (reasoning), Action (tool use), and Observation (seeing results). Inspiration for Module 3's adaptive retrieval loop.
Reproducibility
Ability to Repeat an Experiment
In AI research, the ability to run the same experiment again and get the same results. Requires knowing ALL hyperparameters, dataset splits, random seeds, and code versions. This project directly addresses reproducibility.
S — Z
Self-RAG
Self-Reflective Retrieval-Augmented Generation
A framework where the LLM learns to decide WHEN to retrieve, WHAT to generate, and to CRITIQUE its own outputs using special tokens.
Semantic Scholar
AI-Powered Academic Search Engine
A free academic search engine by Allen Institute for AI. Provides an API used in Module 0 to find BERT-related papers. Includes citation graphs and paper metadata.
Sentence Transformer
Model for Sentence-Level Embeddings
A BERT-based model fine-tuned to produce meaningful sentence-level embeddings using Siamese networks. Unlike BERT where [CLS] is weakly correlated with sentence meaning, Sentence-BERT is specifically trained for semantic similarity tasks.
Sequence Length
Maximum Input Token Length
The maximum number of tokens (word pieces) BERT processes at once. BERT supports up to 512 tokens. Typical fine-tuning: 128 for classification, 384-512 for QA. Longer = more context but more GPU memory.
Siamese Network
Twin Network Architecture
Two identical neural networks that share weights and process two inputs in parallel to produce comparable outputs. Used in bi-encoder architectures (query encoder + document encoder share the same architecture).
Token / Tokenization
Text-to-Number Conversion
Breaking text into tokens (sub-words) and converting them to integers. BERT uses WordPiece tokenization: 'running' → ['run', '##ning']. Each token is mapped to a number in the vocabulary.
Transformer
Self-Attention Neural Network Architecture
The neural network architecture underlying BERT, GPT, and all modern LLMs. Key innovation: self-attention mechanism — every token attends to every other token in the sequence. Proposed in 'Attention Is All You Need' (2017).
TF-IDF
Term Frequency - Inverse Document Frequency
A classical text relevance metric. TF = how often a word appears in a document. IDF = how rare the word is across all documents. High TF-IDF = word is important for this specific document. The basis of many search engines before neural models.
Vector / Embedding
Numerical Representation of Meaning
A list of floating-point numbers (e.g., 384 or 768 numbers) that encodes the semantic meaning of text. Similar texts have similar (close in space) vectors. Foundation of dense retrieval.
Weight Decay
Regularization Parameter (see AdamW)
A penalty term added to the loss function that discourages large model weights. Prevents overfitting. Standard BERT fine-tuning value: 0.01. Must be 0 for Adam but >0 for AdamW.
Zero-shot / Few-shot
Inference without / with few examples
Zero-shot: LLM answers without any task-specific examples — relies purely on pretrained knowledge. Few-shot: LLM is given 2-5 examples in the prompt. Both approaches are used in Paper 8 (survey mentions few-shot retrieval) and Paper 9 (zero-shot baseline evaluated).
